# Архитектура

## Слои

Игровая логика не импортирует DOM. Это позволяет прогонять уровень без браузера — так работает `npm run playthrough` и интеграционный тест.

```text
app/GameApp ──┬── core/       состояние приложения, ввод, события, сохранение
              ├── gameplay/   правила уровня: цели, зоны, обломки, счёт
              ├── physics/    planck-мир, снаряды, связи, разрушение
              ├── render/     отрисовка сцены по снимкам состояния
              ├── ui/         интерфейс поверх сцены
              └── audio/      процедурный звук
```

Поток данных односторонний: ввод и состояние задают параметры, `GameSession.step()` продвигает физику и обновляет цели, рендер читает готовые снимки.

## GameSession

`src/gameplay/GameSession.ts` — центральный объект уровня. Он владеет `PhysicsWorld`, элементами конструкции, зонами, целями и счётом. Наружу отдаёт:

- `snapshot()` — состояние для рендера;
- `refreshObjectives()` — статусы целей после последнего шага;
- `setAim` / `fire` / `unlockAim` — управление запуском;
- `result` — итог уровня, когда исход определён.

Исход вычисляется в `evaluateOutcome()` и наступает при выполнении целей, нарушении ограничения или исчерпании запусков. Пока решение не принято, сессия остаётся в состоянии `running` и ждёт следующего действия игрока — это позволяет стрелять после первой неудачи. `forceEvaluate()` существует для таймаутов и тестов.

## Разрушение

Структура описана как граф: `src/physics/StructuralGraph.ts` строит связи `weld` и `breakable` и пересчитывает их при изменении формы. Физические джойнты создаются через `createWeldJoint`, разрушенная связь исчезает из мира.

Урон считается в `src/physics/DestructionSystem.ts` по энергии столкновения:

```text
reducedMass = (m1 * m2) / (m1 + m2)
energy      = 0.5 * reducedMass * impactSpeed²
damage      = min(maxImpactDamage, energy * damagePerJoule) * damageShare
```

`damageShare < 1` означает, что удар наносит урон не на 100%: цепная реакция затухает вместо того, чтобы сносить всё подряд. Скорость берётся из pre-solve контакта, поэтому расчёт не зависит от порядка шага. Материалы без `destructible` (генератор, земля) накапливают урон, но никогда не переходят в состояние `destroyed`.

Цепные реакции используют исходные координаты схемы, а не позицию упавшей колонны: иначе рухнувшая деталь «попадала» бы в элементы под ней и ломала их без физического контакта.

## Ввод

`InputController` не знает про игровые правила: он хранит координаты указателя, удержание клавиш и набор действий, сработавших в текущем кадре. Источник событий подключается через `attach()`; источник не умеет снимать обработчики, поэтому отписка реализована поколением подписки — старые обработчики перестают влиять на ввод. Это же защищает от повторного `attach()`.

## События

`EventBus` — минимальная шина с `on` / `once` / `emit`. Ошибка в одном подписчике не прерывает доставку остальным. Игровой код публикует события (`shot:fired`, `element:destroyed`, `level:completed`, `settings:changed`), UI и звук на них подписываются.

## Рендер

`SceneRenderer` рисует сцену по `SceneRenderInput`: элементы, зоны, снаряд с trails, камера, эффекты и данные debug-оверлея. Всё рисуется примитивами Canvas2D по палитре `src/render/Palette.ts`, шрифты и картинки не загружаются.

`@napi-rs/canvas` реализует тот же Drawing API, поэтому `SceneRenderer` работает в Node без изменений — контекст просто приводится структурным типом.

## Сохранение

`SaveManager` хранит настройки и рекорды уровней в `StorageBackend` (по умолчанию `localStorage`, при недоступности — память). Любые повреждённые данные проходят через `migrateSaveData`, которая чинит значения по умолчанию и никогда не бросает исключений.
